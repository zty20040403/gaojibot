# Ubuntu Local Acceptance, 2026-09-15

This record concerns a disposable VM on the development Mac. No h310, h610,
tank or other production server was contacted or changed. No developer model
credentials, QQ login state or databases were used. The host Docker engine
and its existing containers were not operated by this check.

## Inputs

- Ubuntu 24.04.5 LTS x86_64, official cloud image build `20260911`.
- Image SHA-256: `612b2c0cc1bc413a6cb8c38fd611794caf0f2b436c50013d8b3794db12ad7354`.
- QEMU TCG: two emulated CPUs, 4096 MiB memory, 24 GiB sparse overlay.
- No host mounts. Generated test SSH keys and a pinned host key; only localhost
  port forwarding. Helper verifies the unique guest marker before operations.
- Initial inspection: systemd present, passwordless sudo for the test user,
  no Docker/PostgreSQL executable, no failed units, 22,107,594,752 free bytes.

## Observed Results

1. Actual app SSH/preflight accepted the clean system. The deployment module
   uploaded its verified bundle and started a persistent systemd installation.
   After the client disconnected, the same job continued installing Docker.
2. Docker and Compose were installed automatically through the Docker package
   repository. No preinstalled container engine was used inside the guest.
3. The original runtime image built, including Whisper, FFmpeg, Python
   dependencies, CJK fonts and Chromium. Its offline acceptance failed before
   database creation: `Unexpected runtime manifest file`.
4. The failure was reproduced with the same immutable image in a non-root,
   read-only, network-disabled container with no user-data mounts. Four
   host-side sandbox recipe entries were incorrectly rejected by the runtime
   source manifest check. The fix recognizes only those exact build files;
   unknown entries, traversal, modified source sizes and hashes remain rejected.
5. The fixed `0.1.10` bundle resumed the original job and instance. Docker reused
   dependency/compilation layers. Runtime acceptance passed, then the job
   entered the database/QQ component stage and completed installation. All 28
   migrations applied; PostgreSQL 17 with pgvector 0.8.6 was healthy, and the
   real QQ component returned an unauthenticated login QR URL. No QQ was logged
   in and the unconfigured Bot was not started.
6. Both original and final packaged macOS apps used real SSH and IPC to connect
   to the guest. The UI check closed/reopened the app, authenticated again
   without remembered credentials, and recovered the same job. It did not
   dispatch another installation. Desktop/narrow screenshots had no horizontal
   overflow and no renderer errors. Only the native file chooser was replaced
   to select the generated QA key; status and network responses were not mocked.

## Real Maintenance Findings

- Service removal completed, retaining the original data. First reinstatement
  failed: it held `install.lock` while synchronously starting the completed
  installer, which needed the same lock. A confirmed retry recovered the same
  task after the installer exited. PostgreSQL system identifier and schema were
  unchanged. The source fix restores the installer definition/boot link but
  does not start this completed bootstrap as a runtime component. A regression
  failed before the fix; related tests pass. A fresh full reinstatement using
  the final source still needs verification.
- A real update used the normal app upload/dispatch protocol, disconnected the
  desktop, created a backup, migrated a candidate database and switched the
  same instance. Its source bundle was
  `aef1b9d6c86bd85a636acad55d638e4aeee8ef551515f1621ea0a588dd59de5f`.
  The `0077` worker umask made the public update directory `0700`, so the app
  could not read progress. Only this VM's redacted status directory was repaired
  to `0755`; private records/logs were not opened. Final source explicitly sets
  owned public-directory permissions and has regressions for this umask.
- The update also reported completion while the controller unit was active but
  its HTTP listener was not yet ready. Retrying the same completed receipt later
  verified the new version and healthy components, without another update.
  Final source waits for an authenticated response from the expected instance;
  its retryable failure does not repeat database migration.
- These are successful recovery observations plus fixes, not an uninterrupted
  final-bundle maintenance pass. Final update/reinstatement/reboot, rollback and
  backup-transfer acceptance remain open.

## Desktop Connection Recovery

An early connection during guest boot produced multiple SSH errors. The old
one-shot listener handled only the first and the second was uncaught. The final
client keeps error handling through teardown, closes failed connections and
distinguishes a network/handshake failure from rejected credentials. Twenty-five
related Node checks passed, including a real localhost TCP peer closing before
SSH handshake. No credential is included in error output.

## Restart Fix

Two focused regressions first failed: a completed installer left a stale public
`running/prepare` projection, and its early return skipped a post-lock purge
check. The installer now re-reads the canonical record after acquiring its lock
and republishes completed status without rerunning installation or changing
the original timestamp. Bootstrap no longer resets existing task status on
ordinary startup. Fifteen source-manifest/installer tests pass, including the
two regressions. Guest-reboot evidence is recorded separately above.
