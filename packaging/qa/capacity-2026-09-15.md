# Desktop Runtime Capacity Admission

## Scope

All work in this record was local. No connection to h310, h610, tank, any
production database, QQ account or model API was made. Docker inventory and
build commands in the unit tests were replaced with fixtures. The later
system-acceptance section uses Docker only inside the project's disposable
localhost VM, not the host's original Docker resources. Temporary HTTP and Unix
socket tests were bound to the development machine.

This is write-admission protection, not a filesystem hard quota. Already-running
commands and concurrent admitted work can still consume space between samples.
Shared images/build caches and engine logs are not charged to an instance, but
their filesystem's remaining space is checked. No automatic deletion was added.

## Implemented Path

- `components.capacity` carries a data budget (default 100 GiB) and minimum free
  space (default 2 GiB), using existing revision checks and backup/restore data.
- The instance manager scans instance files, verified instance-labelled local
  volumes and owned container writable layers. It accounts allocated blocks,
  deduplicates hardlinks, and does not follow symlink contents. Unknown volume
  ownership, unexpected mounts, invalid engine responses and time limits produce
  incomplete results instead of a zero-usage success.
- Background sampling runs independently of automatic retention. Dashboard reads
  consume the cached sample. A sample is published by atomic replacement under
  an owned directory; only that directory is mounted read-only into the Bot.
- Missing, stale (over 180 seconds), malformed or over-budget samples deny new
  sandbox writes/commands and media/video downloads. The Unix sandbox runner
  checks independently before invoking the driver. Existing artifact export,
  read operations, cancellation and cleanup are not denied by this gate.
- Maintenance checks freshly measured capacity before backup/import/restore
  copies. New model downloads and new sandbox builds also check; verified
  existing models and images are still reusable without charging new-download
  headroom. Normal quota checks do not stop an existing process or delete files.
- Legacy non-App runtimes are unchanged unless the capacity-file environment
  setting is explicitly configured. Older managers do not receive unsupported
  capacity settings from the new desktop UI.
