## Boundary

This uses only the existing disposable localhost Ubuntu `restore-target` guest,
instance `09990cc894e04963810403d9a72c25c6`. It contains synthetic migration
fixtures, no configured models or QQ number, and no logged-in QQ account. The

## Defect found by the real test

Uninstall `a4e011c5c49848c8a4d96bcddc90f112` completed, retaining data. Purge
preview `0cafdc00149c40c08d5236c79c711662` contained two containers, one task
workspace volume and one dedicated network. No unrelated fixture was listed.
Confirmation failed safely before deletion, reporting changed data/resources.

An inspection of that exact failed record confirmed:

- The uninstall reference, deployment fingerprint, historical units and
  container resource inventory all still matched the approved preview.
- Reconstructing the controller alone changed the data-tree fingerprint.
- The only changed path was `capacity`: `prepare_directory()` unconditionally
  called `chmod(0755)` even when permissions were already 0755. On both real
  Linux and the local filesystem this changes ctime, invalidating the strict
  deletion snapshot. The failure was terminal/non-resumable; nothing was deleted.

The fix only chmods when permissions differ, after the existing directory,
owner and unsafe-write-mode checks. It does not omit capacity from the snapshot,
ignore ctime, auto-confirm a changed preview or force-delete any resource.

## Regression and packages

Two new tests reproduced the failure before the fix: repeated capacity prepare
changed the filesystem fingerprint, and controller reconstruction invalidated a
real filesystem purge preview. Both pass after the fix. The capacity test also
checks 0700 permission repair and rejection of an unsafe 0777 directory.

63 capacity, purge, resource-inventory and lifecycle tests pass using a local
Python 3.12 QA environment with dependencies from the unchanged `uv.lock`.
The tests run in a temporary working directory with the existing CI SQLite
fixture mode, not the project `.env`, production PostgreSQL or Docker. Initial
runs using the old Python 3.9 environment exposed missing test dependencies;
an unisolated plugin import also lacked a test DSN. Those runs are not recorded
as passes and production configuration was not changed to accommodate tests.

Mac ARM64 and Windows x64 0.1.20 previews contain runtime 0.20.0, 276 files,
checksum `5afd8b94ce929a8502e9669e6b59d34fc015a3c7460c3ef46696de806665ede4`.
Both package/source verifiers pass; the actual packaged Mac passes launch, IPC,
layout, password masking and encrypted backup transfer over localhost SSH.
The narrow screenshot was inspected. Both ZIP CRC checks and Mac DMG integrity
pass. Exact artifact hashes are in `desktop/release/release.json`.
Windows actual execution and signing remain unverified; these are previews.

The first reboot observer incorrectly required every Docker network ID to
survive a daemon restart. Read-only inspection showed only the built-in bridge

for the other two defaults. Exact inventory checks across the purge itself are
unchanged. The same completed purge was re-observed; it was not repeated, and
no instance was recreated or production deletion check relaxed.

The QA scripts preserve original failed attempts. A fixed-runtime retry requires
that original failure to be terminal, a completed App recovery/update for this
same instance, and the current runtime checksum. It then creates a new uninstall
and preview; it never reuses approval for the rejected old data snapshot.

This test deliberately consumes the QA target; afterward the old migration
target must not be silently recreated or used as an installed-instance baseline.
