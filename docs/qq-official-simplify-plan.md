# QQ 官方接入：修 bug + 轻量化方案

> 2026-10-30 起草。读者：负责实现的 AI 执行者。
> 一句话：把 qq-official 从「处处设卡、默认拒绝」改成「默认能用、出错说清楚」，删掉大部分代码，修好线上的 bug。

---

## 0. 先读这一节

### 0.1 为什么要重写这么多

上一版方案（`docs/qq-official-plan.md`）写得太严，实现出来的 qq-official 适配器有 **131 个模块、约 3.1 万行**（不含 2.7 千行协议库和 3.9 万行测试）。线上的问题几乎都来自这些约束：消息发不出去、文件发不出去、回复慢、出了错查不到原因。

同类项目 max（Hank 的 `maxx` 分支，<https://github.com/HCHogan/max/blob/maxx/docs/rust-rewrite.md>，MIT）用大约四千行实现了同样的 QQ 官方接入，线上表现更好。**本方案的方向就是向它看齐**：只参考设计和实测结论，不照抄代码。

### 0.2 工作原则（取代旧方案第 0、5 节的规则）

1. **默认能用**。不再新增任何「证明、证据、版本号必须一致、能力修订号、路由纪元、冻结哈希」之类的前置检查。只有腾讯明确会拒绝的情况，才在本地提前拦下。
2. **出错就说清楚**。错误要写进日志（异常类型、出错的函数和行号，不写消息内容和凭据），并让模型或用户知道发生了什么。不许「静默拒绝」，也不许「静默取消」。
3. **删代码优先**。能用一个简单的东西代替一串模块，就删掉那串模块。每个 PR 的描述里写清楚删了多少行、加了多少行。
4. **测试要有，但只测重要的行为**。每个改动配上针对它的测试；不要求每一步都在本机跑全量测试，全量交给 PR 的 CI。删掉代码时，对应的测试一起删。
5. **不改 OneBot（NapCat）路径的行为**。OneBot 的出站快照测试必须一直通过。
6. 遇到本方案没写到的问题，由你自己判断，选最简单、能用的做法，在 PR 里说一句理由就行。

### 0.3 工作方式

- 在已有的 worktree `/Users/kenneth/Desktop/comp390/bot-qq-official` 里，从最新的 `origin/main` 切出新分支，例如 `fix/qq-official-s0`。每个阶段用一个分支、一个 PR。
- 流程和以前一样：推送分支，开 PR，等 CI 通过，**由用户合并**（选 Create a merge commit）。用户明确说可以自己合并时，才自己合并。
- **部署到 tank 要等用户说可以**。用户同意后，按以前的部署方式发布，发布后按第 5 节的清单检查日志和数据库。
- 不要提交真实的 AppID、AppSecret、openid、群号、QQ 号。

## 2. 改完后应该是什么样

```
腾讯网关
  │
  ▼
收消息：按事件 id 去重 → 跳过机器人自己的消息 → 检查群有没有绑定 → 写入账本 → 判断要不要回复
  │
  ▼
回合：直接用 asyncio 跑共享的模型和工具循环（ChatOrchestrator），不再经过多道持久化任务
  │   模型每写完一节，就交给发送器
  ▼
发送器：每个群一个队列，按顺序发，默认主动消息，超额度就等，Markdown 按小节切
```

- **需要「重启后接着做」的，只有这几类**：Sub-Agent 任务、提醒、例行任务、还没发出去的结果。保留一张简单的待发表（可以直接用现有的 `deliveries` 表）。普通聊天回复不需要持久化。
- **重启时正在跑的普通回合**：启动后在原会话里发一句「刚才重启了，这条没处理完，麻烦再说一次」，并把回合记录关掉。不自动重跑。
- **目标规模**：适配器（`adapters/qq_official/`）从约 3.1 万行降到 **6 千行左右**。这是方向，不是硬指标。

## 3. 分阶段执行

每个阶段一个 PR，按顺序做。**S0 最急**，做完先请用户部署。

### S0：救急（小改动，尽快上线）

只改最少的代码，先让东西能发出去：

1. **主动发送**：
   - 收到 `GROUP_MSG_RECEIVE` 时，把 `proactive_state` 设成 `allowed`；收到 `GROUP_MSG_REJECT` 设成 `denied`。
   - 状态是 `unknown` 时，直接试一次主动发送：成功就设成 `allowed`；返回 40034105 就设成 `denied`，然后退回被动回复。
   - 增加一个查询：`GET /v2/groups/{group_openid}/bot_state`。Hank 实测这个接口不需要管理员权限，返回机器人在群里的身份、**有没有开主动发言**、收全部消息还是只收 @。绑定群时查一次，遇到 40034105 时再查一次，用查到的结果设置状态。
   - 把 `AI_QQ_OFFICIAL_ALLOW_NEWER_WINDOWS` 的默认值改成 `true`：主动发送不可用时，可以借这个会话里最新一条消息的窗口发出去。
   - 部署后，确认卡住的 3898、3899、3913 已经发出（或者已经过期），并在 PR 里写明结果。
2. **搜索**：模型明确传了 `freshness` 就用模型给的；只有没传或者传了 `auto`，才用关键词去猜。把 `freshness` 改成可选参数。
3. **发文件工具**：
   - `send_file_from_sandbox` 同时接受 `/workspace/xxx` 这样的绝对路径和相对路径（只要最终在工作区里面）；
   - 从虚拟机取文件的等待时间加长到 300 秒；
   - 区分「取文件就失败了，所以没发」和「可能已经发出去了」：前者可以重试，防重复机制不能拦。
4. **工具参数**：多出来的字段直接忽略，并记一条 warning，不要报错。
5. **审批检查**：在 `bot_security/service.py` 的异常处理里，记下异常类型和出错的函数、行号。修好之后，根据日志找到真正的原因，在同一个 PR 或下一个 PR 里修掉。
6. **`RESUMED` 事件**：当作网关的控制事件处理，不进收件箱，不算隔离。
7. **数据库连接池**：`AI_POSTGRES_POOL_MAX_SIZE` 改成 20 到 30。具体数值你来定，要考虑官方接入新增的几个常驻后台任务也要占连接。
8. **回合记录**：`agent_turns` 记录实际回答的模型和 profile（发生回退时记回退后的那个）。
9. **沙盒镜像**：装上 `pip`。或者在工具说明里写清楚已经预装了哪些 Python 包，二选一。
10. **重启被打断的回合**：启动时找出状态是 `running` 或 `turn_execution_interrupted` 的回合，发一句「刚才重启了，这条没处理完，麻烦再说一次」，然后把记录关掉。

验收：在测试群里让机器人做一个需要超过 5 分钟的事，结果能送到；让它做一个 PDF，能收到文件。

### S1：重写发送部分

把发送部分换成一个简单的发送器，删掉窗口预算、试探和证明那一整套。

**新的发送器**（大约几百行）：
- 每个端点（群或私聊对象）一个 `asyncio` 队列，按顺序发。
- **默认主动发送**。群状态是 `denied` 时，退回被动回复：用这个会话里最新一条入站消息的 `id`，要求 5 分钟内、次数没用完（群聊 5 次、私聊 4 次，在内存里计数），`msg_seq` 每次加一。被动回复也用不了时，告诉模型或用户「这个群没开主动发言，请群主打开」，再写进日志。**不挂起 24 小时**。
- **额度**：整个机器人每分钟 60 条，每个群每分钟 20 条。超了就 `sleep` 等，不丢。每天 1000 条的上限靠腾讯返回的错误兜底，不需要持久化计数。
- **错误处理**（照 Hank 的做法）：
  - 腾讯明确拒绝（返回了错误码）或者根本没连上 → Markdown 被拒就改发纯文本，只重试一次；
  - 请求已经发出去，但超时或者回包解析失败 → 记成「不确定」，**不重发**，告诉模型「（可能没发出去）」；
  - 40034006（内容违规）→ 失败，不重试；
  - 401 → 刷新 token，重试一次；
  - 429 或频率限制 → 等一会儿再发。
- **记账**：成功后照常写账本、写 `turn_send_links`，并记下返回的 `id` 和 `ext_info.ref_idx`，以后用于引用。

**删除**：`send_policy.py`、`rate_policy.py`（换成几十行的令牌桶）、`outbox.py`、`receipts.py`、`settlements.py`、`plans.py`、`protected_plans.py`、`outbox_types.py`、`format_fallback.py`、`error_policy.py` 等，以及 `qq_official_reply_windows`、配额周期这些只在这套逻辑里用到的表（表等 S9 再删，代码先删）。【你来判断】具体删哪些、哪些逻辑并进新发送器。

### S2：边生成边发送，按小节分段

- 打开流式：模型每写完一节就发出去，不等整个回答结束。
- **切分规则**（Hank 实测）：
  - 出现标题之后，**每个标题开始一条新消息**，同一节里的表格和列表跟着这一节一起发；
  - 第一个标题之前的内容，按空行切；
  - 分隔线 `---` 一律不单独发，直接删掉；
  - 一条超过长度上限时，再按段落切。
- **QQ 的 Markdown 有几个怪处**：单个换行就会断行；行尾两个空格会多出一个空行；粗体后面紧跟的空格会被吞掉；`\[…\]` 不支持，要换成 `$$…$$`。
- 在提示词里告诉模型：长回答用 `###` 分节。
- 进度提示（「正在生成 PDF~」这类）走同一个发送器，作为普通的主动消息发出。

### S3：重写文件发送

参照 Max 的 `send_file`：

- 工具 `send_file(path, name?)`：从这个群的沙盒里读文件（绝对路径或相对路径都行），上传，再发送。**任何格式都可以**，只要带上文件名。图片用 `file_type=1` 发（GIF 也行，会动），其他文件用 `file_type=4` 并带上 `file_name`。
- **上传**（Hank 实测）：
  - 5 MiB 以内用 base64 一次传完（6 MiB 能过，8 MiB 会报 850012）；
  - 超过 5 MiB 就分片：`upload_prepare` 要带 `file_type`、`file_name`、`file_size`、`md5`、`sha1`、`md5_10m`（前 10,002,432 字节的 MD5），少一个摘要就报 850012。返回 `upload_id`、`block_size` 和每一片的预签名地址；把每片 PUT 上去，再调 `upload_part_finish`（带 `upload_id`、`part_index`、`block_size` 和这一片的 MD5）；最后对 `files` 接口发 `upload_id`，拿到 `file_info`。
  - `file_info` 按（会话、SHA-256、文件名）缓存一天。
- 然后用 `msg_type=7` 发送，带上 `media.file_info`。
- **出错时**：报 50015014 就再调一次 `upload_prepare` 查真实原因（Hank 遇到的是 40093003「群文件超过上限」），把原因告诉模型和用户。
- 单个文件上限 100 MB，每天累计 2 GB（腾讯 OpenClaw 插件 README 里的数字），超了就告诉用户。下载链接这条路先不做，确实需要时再加。

**删除**：`host_config` 里的 `native_routes` 和证明机制；`file_links.py`、`file_artifacts.py`、`file_services.py`、`file_dispatcher.py`、`file_runtime.py`、`file_payloads.py`、`file_publications.py`、`file_authority.py`、`file_projection.py`、`file_generation.py`、`native_upload.py`、`native_chunk_dispatch.py`、`native_part_transport.py`、`native_vault.py`、`native_session_vault.py`、`download_runtime.py`、`protected_payload.py` 等。【你来判断】哪些逻辑并进新的上传代码。

### S4：每个群一台常驻虚拟机

- 每个群（会话）一台沙盒虚拟机，第一次用时创建，**之后一直复用**。空闲超过一段时间（例如 2 小时，由你定）再停掉，`/work` 目录保留。
- 开机是这台虚拟机的事，不是每个任务的事。可以在群第一次有消息时就提前开机。
- **guest agent 没有响应时**：工具调用要等它恢复（例如每 2 秒检查一次，最多等 60 秒），而不是直接失败或者超时后变成「不确定」。
- 工作区和虚拟机的清理：按最后使用时间，过期自动清理。
- 这一块涉及 `sandbox_runtime` 和 `vm_sandbox` 的已有代码。OneBot 路径能不能一起受益，由你判断；不影响 OneBot 的行为是底线。

### S5：Sub-Agent 简化

1. **结果交回前台**（参照 Max）：任务完成、部分完成、失败、超时，都把报告交回前台模型，由前台决定怎么在群里说、要不要用 `send_file` 发文件。结果送达照样走 S1 的发送器，不再等回复窗口。
2. **部分完成也要交付**：独立验收改成「建议」而不是「关卡」。验收的意见附在报告里，已经生成的文件照样可以发。
3. **用户要文件，就必须产出文件**：任务目标里有「做成 PDF、表格文件」之类的要求时，规划阶段要把「生成文件，并写到 `/work` 里」作为交付物；写文档的步骤结束前检查文件是否存在，不存在就让它补上。
4. **工具调用上限**：单轮上限放宽（task#180 被拒了 18 次）；`web_search` 的 `freshness` 改成可选（S0 已修）。
5. 【你来判断】多角色流水线要不要收缩成「一个 agent 干到底」。最低要求是任务跑通、能交付，不追求一步到位。

### S6：收消息和回合链路简化

- 现在一条消息要经过：收件箱入库 → 入库任务 → 回合任务 → 发送计划 → 发件箱 → 发送器。改成：网关事件 → 去重（数据库唯一约束就够了）→ 写入账本 → 直接开一个 asyncio 任务跑回合 → 发送器。
- 去重只需要两条：（端点，事件 id）和（端点，消息 id）。
- 机器人自己的消息会被推回来（生产库里有 38 条 `bot_origin`），继续按「是不是机器人发的」跳过。
- 跨重启续连：保留现有的 session id 和序号持久化（这块是好的）。服务端补发的旧消息，按平台 id 去重即可。
- **删除**：`execution.py`、`turn_consumer.py`、`turn_runtime.py`、`turn_lifecycle.py`、`settlements` 相关、`lease.py` 里与此无关的部分、`command_fence.py`、`control_receipts.py` 等。单实例锁（advisory lock）保留，但要简化。

### S7：历史迁移、身份、审批、项目权限简化

- **历史迁移**：用 Hank 的做法代替现在约 20 个 `migration_*` 模块（约 5 千行）：owner 私聊发 `/bind <老群号>` 拿到 6 位码，在新群里发 `/bind <码>`，这个群就接到老会话的时间线上，从此照常往下记。不需要预览、冻结、审批、核验这一套流程。
- **Historian**：不再受迁移状态影响，照常工作。

## 5. 每个阶段上线后检查什么

在 tank 上只读检查（数据库连上后先执行 `set default_transaction_read_only=on`）：

1. 日志里没有新的 ERROR；`Mobile authorization background check failed` 不再出现。
2. 发送指标里出现 `mode="proactive"`；`deliveries` 里没有新的 `waiting_reply_window` 或 `unsolicited_window_unavailable`。
3. 回合耗时：普通聊天收到第一条回复不超过 10 秒（模型够快的前提下）；带工具的回合，群里能看到中间进度。
4. 在测试群里让机器人：
   - 写一份 PDF 并发过来；
   - 发一个大于 5 MiB 的文件；
   - 做一个超过 5 分钟的 Sub-Agent 任务，能收到结果；
   - 回答一个带表格和代码块的长问题，按小节分条发出，不出现单独的 `---`。
5. 重启服务一次：正在跑的回合会收到「刚才重启了」的提示；`agent_turns` 里没有残留的 `running`。
