# 高级 App 第一版实施方案

状态：设计方案，尚未实现。日期：2026-09-14。

> 后续需求已调整：用户要的是在干净服务器上全自动部署的 macOS / Windows 客户端，而非默认在电脑上运行机器人。以 `server-app-v1-plan.md` 为当前实施范围；本文的本机运行假设不再作为首发目标，功能兼容、隔离、交付和恢复要求仍保留。

## 1. 产品目标与范围

用户安装 App，用自己的 QQ 扫码登录，填写自己的模型服务和 API Key，选择群聊，即可运行独立机器人。用户不需要配置数据库、Python、Nix、端口或环境变量。

每个安装拥有独立配置、数据库、QQ 会话和文件目录。默认不依赖开发者的 h610、tank、内网模型或任何私人凭据。用户选择的模型、搜索、语音等外部服务仍可能接收处理所需的数据，应逐项说明。

第一版不做 VIP、支付、积分、强制注册或开发者云托管。保留现有能力，按环境和依赖分为默认可用、按需安装、需要自行接入三类；不把“按钮存在”视为功能完成。

本方案建议首发 Windows 11 x64，先完成一个真实可验收的桌面版本。macOS Apple Silicon 为下一平台；现有 Linux/NixOS 服务器部署继续维护。此平台顺序是计划选择，不是当前已有支持承诺。

本机必须保持开机联网。默认关闭窗口进入托盘；明确退出才停止本机机器人。开机启动由用户选择。睡眠期间不承诺在线，恢复后重新核对连接和持久任务。

## 2. 基于当前项目的技术选择

- 保留 Python / NoneBot / FastAPI / Agent 核心，不重写业务逻辑。
- 复用 `admin-ui` 的 React + TypeScript 页面、管理 API 和 SSE。
- 桌面壳选择 Electron，增加受限的本机运行管理接口。接受其基础体积，优先复用现有前端技术。
- Python 后端先验证 PyInstaller 目录式打包，包含解释器和必要资源。针对目标系统构建，不把 Nix 产物当成 Windows 可执行文件。
- 继续 PostgreSQL，随组件包提供已验证版本，或首次安装下载固定版本。第一版不引入 SQLite 双实现。
- NapCat 使用固定、已验证的发行组件；许可证、QQ 客户端分发条件和兼容性必须核对后再决定哪些可直接内置。
- Docker 仅用于需要隔离执行的高级组件。未安装时基础聊天必须可用；其安装和系统权限要求必须显式告知用户。
- 现有 Nix Flake 与 NixOS module 保留用于服务器，不成为桌面用户的安装前置条件。

当前核对发现：`flake.nix` 未包含 Windows 平台；生产部署要求 PostgreSQL；集群配置存在默认 `h610` 主机名。因此跨平台打包与配置去个人化都是真实工作，不是换一个窗口图标。

## 3. 运行结构

```text
桌面窗口：设置、状态、任务、文件、诊断
    |
受限 IPC：固定操作、参数校验、调用方校验
    |
本机运行管理器
    +-- PostgreSQL：初始化、健康检查、正常启停
    +-- NapCat：QQ 登录、连接状态、重新认证
    +-- Gaoji Python Runtime：会话、模型、工具、任务、投递
    +-- 可选组件：浏览器、媒体工具、Docker 沙盒

用户私有数据目录
    +-- config：实例设置，不包含可公开分发的密钥
    +-- database：数据库数据
    +-- files：附件、表情、任务产物
    +-- cache：可重建缓存
    +-- logs：脱敏日志
    +-- backups：有限保留的可恢复备份
```

安装文件和用户数据分开。运行管理器在窗口关闭后继续工作，单实例锁阻止同一个数据目录被重复启动。不得通过进程名批量终止用户其他 Python、PostgreSQL、QQ 或 Docker 进程。

## 4. 按顺序实施

### M0：兼容性验证与功能清单

先在干净 Windows 环境验证：Python 依赖、插件动态加载、数据库迁移、PostgreSQL 启停、NapCat 登录和一条真实 QQ 回复。重点核对音频本地库、CodeSnap、浏览器和需要 Linux 的工具。

建立功能兼容表，逐项填写平台、依赖、凭据、状态、缺失原因和验收案例。不兼容的工具明确选择 Windows 实现或隔离 Linux 组件，不用空实现伪装支持。

验收：不依赖开发机环境也能完成最小收发；明确所有现有功能的承载方式。Windows 构建和验收环境未准备好时，不宣称 Windows 版本完成。

### M1：独立发行配置

增加桌面运行配置与服务器配置的明确边界。首次创建全新实例，生成实例 ID、数据目录和内部认证凭据。

发布包不携带现有数据库、QQ 会话、API Key、管理员 QQ、群白名单、内网路由、私人模型配置或个人提示词。示例配置不得默认访问开发者内网。

模型只从用户配置中选择；无模型时进入未配置状态，不能静默使用开发者 Key。用户选择的聊天、视觉、Embedding 和搜索服务分别检查能力及凭据。

验收：断开开发者 Tailscale，在新用户目录启动；没有任何对开发者私人基础设施的必需请求。原服务器部署方式保持可用。

### M2：组件安装与运行管理器

增加组件清单，记录版本、平台、来源、校验值、安装体积、许可证和健康检查。提供下载进度、失败重试和可恢复安装，下载文件通过可信发布清单校验后再运行。

先启动数据库，执行适用的数据库迁移并检查，再启动 Runtime 和 QQ 接入。停止时先停止接收新任务、保存状态，再按依赖关系停止服务。

使用固定程序路径和参数数组启动组件，不接收 UI 或模型传来的任意 Shell 命令。组件崩溃可以有限重试；持续失败进入错误状态，不能无限重启或反复刷新 QQ 登录。

验收：启动、停止、重复打开、后台组件崩溃、断网和睡眠恢复有明确状态；不影响用户已安装的数据库、QQ 和其他程序。

### M3：用户无感的本地 PostgreSQL

用独立用户数据目录初始化数据库，固定已验证的大版本，只监听本机。生成独立强凭据，明确认证策略，不能为了省事启用宽泛免密访问。

处理端口冲突与已有 PostgreSQL 共存。应用运行账号采用所需的最小数据库权限，迁移凭据与日常运行权限区分。API Key 优先保存到系统凭据存储，不写日志或普通设置导出。

提供健康检查、空间检查、有限数量备份、导出和恢复。逻辑备份或受控停机备份均需恢复验收，不直接复制运行中的数据目录作为“成功备份”。

验收：用户不填写 DSN；重装程序和升级不丢数据；备份能在全新目录恢复；磁盘不足时不反复写满磁盘或重新初始化已有数据库。

### M4：首次配置向导

流程：环境检测 → 安装必要组件 → QQ 扫码 → 配置模型 → 选择群与人设 → 验证收发。

二维码由用户自己的 NapCat 会话生成；设备确认交给用户。保留登录状态，区分登录失效、网络失败和接入组件崩溃，不因一次探测失败清空会话。

模型配置提供服务商预设和自定义兼容地址。模型列表请求不代表模型实际可用；用户点击连接测试后才做小规模真实调用，并提示可能产生 API 费用。视觉和工具调用能力不凭名称猜测。

首次明确选择机器人管理员和启用群。默认关闭主动插话、全体提醒、宿主机执行及服务器控制，按用户选择开启。

验收：普通用户无需命令行完成登录、配置和第一条回复。错误 Key、模型不存在、二维码失效等均能定位到具体步骤并继续，不必卸载重装。

### M5：全部现有能力产品化

| 能力组 | 第一版处理方式 | 关键验收 |
| --- | --- | --- |
| 聊天、人设、群与私聊、引用和 @ | 默认提供 | 不串群、不把其他用户记忆当当前用户事实 |
| 多模型、推理强度、降级与用量 | 默认提供 | 清楚展示期望模型、实际模型、原因；不使用未配置的服务 |
| 上下文、章节、长期记忆 | 默认提供适用能力 | 缺少 Embedding 时仍可聊天；配置后能验证召回 |
| 图片与表情、语音、文件、帖子和视频 | 按需组件和对应模型/服务 | 真正读到内容；缺少能力时明确说明；生成中文文件能正常显示 |
| Agent、子 Agent、任务恢复 | 核心编排保留 | 子任务独立上下文、并行状态真实、失败不被汇总成全部成功 |
| 浏览器、沙盒、代码、构建和预览 | 组件安装后启用 | 隔离执行、资源受限、中文渲染正确、文件实际交付 |
| 多实例与多个 QQ | 独立配置与状态目录 | 每个实例登录、工具、缓存和数据隔离；共用二进制而非重复下载 |
| 集群、Worker、运维与告警 | 用户接入自己的基础设施后启用 | 无配置不查询开发者服务器；权限与操作结果可验证 |
| Matrix / iMessage 等现有桥接 | 保留为高级连接器 | 明确外部桥接和平台依赖；不声称所有系统都能本机运行 |

功能均不设付费门槛，但“全部保留”不等于所有依赖默认安装。功能页展示可用、未配置、缺少组件、当前平台不支持四类状态，并提供对应处理入口。

沙盒构建使用固定版本的预构建镜像或增量层，仅依赖发生变化时更新，不随每次 App 更新重新生成巨型镜像。显示组件、缓存和镜像实际占用；不得执行全局 Docker/Nix 清理来维护本应用。

群消息、网页和文件都属于不可信输入。沙盒不能默认挂载用户主目录、密钥、宿主数据库或 Docker socket；确需容器控制的接口必须收窄到本实例资源。

验收：兼容表所有功能都有实测结果；无法承载的明确列为平台限制，不把限制隐藏为通用失败或假装成功。

### M6：桌面界面与诊断

复用现有 React 控制台，增加首次配置、实例切换、组件管理、启停和托盘。日常入口包括概览、QQ 与群、模型、人设与记忆、任务与成果、组件、存储与诊断。复杂集群和调试功能放到高级视图，不删除已有页面。

状态通过 SSE 增量合并，不能重建整个页面导致下拉框、输入草稿、展开状态和滚动位置消失。只有小范围本机运行状态使用轻量轮询，不能每秒重新扫描整个数据库或文件系统。

错误区分 QQ、模型、数据库、下载、权限、磁盘和外部平台限制。诊断包默认脱敏，包含版本、状态和必要错误，不含 Key、QQ 登录态、原始聊天和文件内容。

验收：后台更新时仍可编辑；错误原因可定位；安装未完成或 Runtime 未启动时，桌面仍能打开诊断页。

### M7：持久任务、交付和数据生命周期

沿用持久任务、租约与 Outbox，并对桌面关机、睡眠、断线和更新中断专项验收。不以命令退出码代替任务验收，也不以发送请求完成代替文件已交付。

回执不明时持久记录并核对，不盲目重发；非幂等操作恢复时先确认执行结果，不能重复操作服务器。无法核实时明确标记未验证，不承诺不可实现的绝对仅一次投递。

缓存、任务产物、用户文件和数据库分别制定保留策略。待投递产物受保护，同时受磁盘总量预算约束；临近空间或保留上限时暂停新产物任务并通知用户处理，不无限囤积，也不无提示删除未交付文件。

验收：中断后任务状态仍在；产物可找到；有明确最终成功、部分完成、失败或待处理状态，不能只停在“正在处理”。

### M8：发布、升级与卸载

App、Python Runtime、NapCat、数据库及可选组件建立兼容版本清单。先完成手动下载安装更新，再做经过签名校验的应用内更新，不把运行远程脚本当作更新方案。

应用升级前检查空间和活动任务，必要时暂停新任务并备份。数据库大版本升级走单独迁移流程；仅在结构兼容时允许程序直接回退，否则通过已验证的备份恢复流程处理。

卸载默认保留用户数据，“彻底删除”要求单独确认。清理仅覆盖本应用管理的资源，不卸载共用 Docker、不删除其他镜像和数据库、不修改用户服务。

验收：完成真实安装包、签名流程、依赖与许可证清单、干净环境安装、升级、失败恢复、卸载保留数据和重新安装恢复。没有拿到签名或实际平台验证时标为预览版，不称为正式发布。

## 5. 发布验收与资源边界

采用分层验收，不每次跑大量付费模型测试。日常修改以组件测试和模拟模型为主，候选发行版跑少量真实 QQ 和自有测试 Key 冒烟用例。

必测场景：首次安装、中文路径、普通用户权限、端口冲突、错误 Key、QQ 重登、无 Docker 聊天、有 Docker 交付、中文 PDF、子 Agent 并行、进程重启、睡眠恢复、网络中断、磁盘不足、升级失败、备份恢复和两实例隔离。

涉及服务器修改的验收只在专用测试目标执行。不能把用户的现有 h610、tank 或同学的服务当作默认测试环境。

记录安装包及下载体积、基础待机 CPU/内存、启用各组件后的增量、启动耗时和磁盘增长。M0 测量后确定发布预算；在测量前不承诺“几十 MB”或任意性能数字。

QQ 第三方接入兼容性、模型服务可用性和各平台登录限制属于外部依赖。产品能识别、提示和恢复，但不能承诺永不掉线、永不验证或所有网站都能读取。

## 6. 交付物与开发边界

建议新增目录：`desktop/` 管理桌面壳与受限 IPC；`packaging/` 管理组件清单、平台构建与安装；`src/local_runtime/` 管理本机生命周期。仅在接口确定后创建，不复制整份业务代码形成两个难以同步的 Bot。

交付物包括：独立安装包、组件清单、首次配置向导、完整功能兼容表、恢复/更新流程、用户说明和验收记录。所有用户功能可用性由配置、依赖与安全权限决定，不包含会员等级判断。

在独立分支或 worktree 开发。每个里程碑有验收记录再进入下一步；不替换线上数据库，不复制线上密钥，不为开发桌面版 rebuild 用户现有集群。

推荐首个开发切片：M0 + M1 + M2/M3 的最小闭环，让干净电脑上的独立数据库、Runtime 和 QQ 接入真正启动，再扩展向导与全部组件。M0 到 M8 是实施顺序，不代表已经完成。
